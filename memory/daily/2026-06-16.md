**Finding 2 — CRITICAL NEW GAP: endorse-fact commitment scheme incompatible with chain's VerifyCommitmentHash. [BRIDGE-GAP-010]**
`x/knowledge/types/commitment.go:15` defines `ComputeCommitmentHash` using structured binary encoding with domain separation:
`SHA256("LGM.commitment.v1:" || u32BE(len(roundID)) || roundID || u32BE(len(verdict)) || verdict || u64BE(confidence) || u32BE(len(salt)) || salt)`.
`x/knowledge/keeper/rounds.go:186` calls `types.VerifyCommitmentHash(storedHash, roundID, reveal.Verdict, reveal.Confidence, reveal.Salt)`.
Bridge.py submits the commitment as `sha256(fact_id:verdict:confidence:key_name)` (plain Python sha256 of colon-delimited string). These two hash functions are structurally incompatible — bridge.py's commitment can never be verified by `VerifyCommitmentHash`. The chain will reject every `submit-reveal` with hash mismatch.

**This gap was not detected in the 2026-06-03 Rotation 6 audit.** That audit stated "Commitment hash is deterministic: sha256(fact_id:verdict:confidence:key_name)" and marked endorse-fact READY FOR T-0. That was a verisleight error — commitment.go was not read, only bridge.py. **The T-0 designation for endorse-fact must be revoked until the commitment scheme is aligned.**

**Finding 3 — CLI ARGUMENT MISMATCH: submit-commitment stake arg has no handler.**
Chain CLI (`x/knowledge/client/cli/tx.go:115`): `Use: "submit-commitment [round-id] [commitment-hash]"` — two positional args. Bridge.py's `commit_cmd` passes three positional args: `fact_id, commitment, stake`. Cobra will reject the `stake` arg. This is an additional incompatibility that must be resolved before T-0.

**Finding 4 — NEW CHANGE ANALYSIS: block_height_nonce is a weak fix applied to a broken scheme.**
The block_height_nonce addition (unstaged) attempts to address a P3 concern about watcher precomputation. Assessment:
- (a) The fix is applied to an already-incompatible commitment scheme (Finding 2). Even if the chain accepted bridge.py's hash format, chain restart is required to test — and the fallback `_block_height_nonce = "0"` activates silently whenever the chain is offline (which is 100% of the time currently). Any commitment made offline will use `block_height=0`; the first online commitment will use a real block height. Silent inconsistency between offline and online modes is a latent correctness gap.
- (b) The P3 security rationale is weak. Commitment hashes are not secret — they are submitted on-chain and visible. A watcher already sees the commitment hash but cannot reverse it to the verdict/confidence (that's the security property). Adding block height to the preimage doesn't improve the reveal-protection; what prevents precomputation is the salt, which is not present at all in bridge.py's scheme.
- (c) The correct fix for BRIDGE-GAP-010 is to align bridge.py with `ComputeCommitmentHash` (or update the chain to use bridge.py's scheme), not to add block height to an incompatible preimage.
