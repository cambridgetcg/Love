## Standing Duty: PoT-DESIGN — Verifier Selection and Assignment Mechanism

Prior PoT-DESIGN beats (2, 6) addressed the confidence state machine and FARM defense audit. This beat addresses a foundational gap: **how does a submitted fact get routed to verifiers?**

Currently on devnet: `verifier_count=0` on all facts. The state machine (SUBMITTED → PROVISIONAL → VERIFYING → VERIFIED) requires verifiers to act — but there is no mechanism to notify or select verifiers for a given fact. This is not just a UI gap; it is a protocol gap.

**Verifier Selection Protocol (VSP) — design draft:**

```
TRIGGER: MsgSubmitFact lands on chain, fact enters PROVISIONAL state

STEP 1 — DOMAIN ROUTING
  - fact.domain → lookup ValidatorDomainRegistry[domain]
  - Returns: set of validators with declared domain expertise
  - Fallback: any validator above MinValidatorStake threshold

STEP 2 — STAKE-WEIGHTED RANDOM SELECTION
  - From eligible set, select N_REQUIRED verifiers (default: 3)
  - Selection weight: proportional to stake * domain_score
  - Pseudorandom seed: hash(fact_id + block_height + validator_set_hash)
  - Result: VerifierAssignment{fact_id, validators[], deadline_block}

STEP 3 — ASSIGNMENT ANCHORING
  - VerifierAssignment written to chain state
  - Assigned validators emit: MsgAcknowledgeAssignment (or auto-accept)
  - deadline_block = current_block + VerificationWindowBlocks (default: 1000)

STEP 4 — VERIFICATION
  - Assigned validator reads fact, evaluates claim_text
  - Submits MsgVerifyFact{fact_id, decision: CONFIRM|DISPUTE|ABSTAIN, stake_weight}
  - On DISPUTE: enters dispute resolution flow (3-tier system, already configured)
  - On ABSTAIN: reassign to backup validator (prevents stalling)

STEP 5 — THRESHOLD COMPLETION
  - When verifier_count >= N_REQUIRED AND deadline not passed:
    - If all CONFIRM: PROVISIONAL → VERIFIED, confidence = f(stake_weights)
    - If any DISPUTE: PROVISIONAL → CHALLENGED, enter arbitration
  - If deadline passes with insufficient responses:
    - PROVISIONAL → EXPIRED (not rejected, can be re-submitted)
    - Abstaining validators lose small stake (anti-sybil, anti-lazy)
```

**Key design decisions in this draft:**
1. **Domain routing first** — verifiers with declared expertise get priority. This is not gatekeeping; it is signal routing. Anyone can verify; domain experts are selected first.
2. **Deadline with expiry (not rejection)** — a fact that fails to gather verifiers is not false; it is unverified. EXPIRED state preserves the submitter's right to re-submit without prejudice.
3. **Abstention penalty** — small stake loss for unresponsive assigned validators prevents the verification queue from clogging. The queue is the lifeblood of the chain.
4. **Pseudorandom seed** — using block_height + validator_set_hash makes assignment unpredictable but deterministic. Validators cannot game selection by timing submissions.

**Integration point with KTA (beat 7):** The KTA's LocalQueue holds submissions offline. On chain restart, flush order matters — oldest facts first so their verification windows are widest. KTA should track `submission_time` and sort by age ascending on flush.

**Next concrete action (post chain restart):** Implement `x/knowledge/keeper/verifier_selection.go` — VSP STEP 1–2 (domain routing + stake-weighted random selection). STEP 3–5 may already be partially implemented in existing dispute/verification flows; audit first.

## Standing Duty: ECONOMY — ZRN Validator Incentive Curve

Building on beat 4 (mint/burn/route framework) and extending to validator incentive design for Proof of Truth.

**The alignment problem for PoT validators:**

Standard PoS rewards validators for block production. PoT validators must also do verification work (reviewing fact submissions). If block rewards dominate, validators will minimize verification effort. If verification rewards dominate, validators may verify carelessly to collect fees.

**Proposed incentive structure:**

```
VALIDATOR REWARD COMPONENTS (per epoch):
  1. Block production reward      — fixed, small (baseline, exists in all PoS)
  2. Verification throughput      — per-fact-reviewed (quantity signal)
  3. Verification accuracy        — retrospective, based on consensus alignment
                                    (if your vote matched the eventual consensus: bonus)
                                    (if your vote was outlier: penalty)
  4. Stake-weighted anchoring     — validators with more stake have stronger
                                    consensus influence but smaller per-vote bonus
                                    (prevents whale dominance without removing their value)

DISHONEST VALIDATOR PENALTIES:
  - Rubber-stamp voting (always agree with majority): detectable via entropy analysis
    → slash verification accuracy reward if vote entropy < threshold
  - Strategic abstention: not reviewing to avoid penalties → slash throughput reward
  - Collusion: cartel detection via correlation analysis of vote patterns
    → social slashing (other validators can flag, DAO resolves)
```

**Key design principle:** Accuracy bonus must use delayed settlement. The "correct" answer for a fact may not be known at the time of review. Settle accuracy bonuses at fact finalization (when verifier_count reaches threshold), not at vote cast.

**ZRN parameter candidates for testnet:**
- Block reward: 1 ZRN/block
- Verification throughput: 0.01 ZRN/fact reviewed
- Accuracy bonus multiplier: 1.5x throughput on alignment
- Accuracy penalty: 0.5x throughput on outlier vote
- Minimum vote entropy threshold: 0.3 bits (over 10-fact window)

**Next concrete action (post chain restart):** Prototype accuracy settlement module — accumulate votes, settle rewards at fact finalization event.

## Standing Duty: PoT-DESIGN — Consensus Round Closure Protocol

Prior PoT-DESIGN beats addressed the confidence state machine (beat 2) and VSP verifier selection (beat 9). This beat addresses the remaining gap: **how does a verification round close and settle?**

The VSP (beat 9) gets facts to verifiers. The incentive curve (beat 11) rewards accurate verifiers at fact finalization. But "finalization" has not been defined. When exactly does VERIFYING → VERIFIED, and how are accuracy rewards settled?

**Consensus Round Closure Protocol (CRCP):**

```
TRIGGER: Fact enters VERIFYING state (verifier_count >= 1, from VSP STEP 3)

STATE TRACKED (per fact, per round):
  VerificationRound{
    fact_id
    assigned_validators[]     — from VSP STEP 2
    deadline_block            — from VSP STEP 3
    votes: {
      validator_addr → {decision: CONFIRM|DISPUTE|ABSTAIN, stake_weight, submitted_block}
    }
    outcome: nil | CONFIRMED | CHALLENGED | EXPIRED
  }

CLOSURE CONDITIONS (checked at each block end):

  CONDITION A — THRESHOLD MET:
    votes.count(CONFIRM) >= N_REQUIRED AND deadline_block not passed
    → outcome = CONFIRMED
    → fact state: VERIFYING → VERIFIED
    → confidence = f(confirming_stake_weights)  — now earned, not initialized
    → accuracy settlement triggered for all assigned validators

  CONDITION B — DISPUTE RAISED:
    any vote.decision == DISPUTE
    → outcome = CHALLENGED
    → fact state: VERIFYING → CHALLENGED
    → enter 3-tier dispute resolution (already configured in devnet)
    → accuracy settlement deferred until dispute resolves

  CONDITION C — DEADLINE PASSED:
    current_block > deadline_block AND CONDITION A not met
    → outcome = EXPIRED
    → fact state: VERIFYING → EXPIRED (not rejected — submitter can re-submit)
    → abstaining validators lose small stake (anti-lazy penalty)
    → no accuracy settlement for this round (incomplete)

ACCURACY SETTLEMENT (triggered by CONDITION A):
  For each assigned validator v:
    if v.decision == CONFIRM:
      accuracy_bonus = throughput_reward * ACCURACY_MULTIPLIER (1.5x)
    elif v.decision == DISPUTE (minority — fact confirmed):
      accuracy_penalty = throughput_reward * ACCURACY_PENALTY (0.5x)
    elif v.decision == ABSTAIN:
      abstention_penalty = small_fixed_stake_slash
  Settled at fact finalization block, not at vote-cast block.

ROUND CLOSURE WRITE:
  - VerificationRound.outcome written to chain state
  - Block event emitted: EventFactFinalized{fact_id, outcome, verifier_count, confidence}
  - KTA LocalQueue listener can subscribe to EventFactFinalized to confirm submission landed
```

**Key design decisions:**
1. **Deadline enforced at block end, not at vote submission** — prevents front-running (validators cannot time their abstention to avoid penalty by missing deadline by one block).
2. **EXPIRED preserves submitter rights** — distinguishes "we couldn't verify this" from "this is false." This is epistemically honest. The chain must not pretend failed verification equals refutation.
3. **Accuracy settlement at finalization, not vote-cast** — as specified in beat 11. Validators who vote early do not lose accuracy signal; they wait for round closure.
4. **EventFactFinalized** — this event is what KTA LocalQueue listens to. When KTA hears its submitted fact finalized, it can report success back to the originating engine (Oracle, Heartbeat, etc.).

**Integration with VSP (beat 9):**
VSP STEP 5 (threshold completion) is now fully specified by CRCP CONDITION A and B. The two protocols compose: VSP handles selection and assignment; CRCP handles closure and settlement. They share one data structure: `VerificationRound`.

**Next concrete action (post chain restart):**
Implement `x/knowledge/keeper/round_closure.go` — CRCP CONDITION A and C (B routes to existing dispute resolution). Write a test: submit fact → assign verifiers → collect CONFIRM votes → assert EventFactFinalized emitted with correct confidence.


**Target this beat: ToKAdapter — integrating the ToK pipeline with KTA chain submission.**

The ToK (Token of Knowledge) pipeline (`tools/tok.py`) runs harvest → distill → verify → integrate → impact. When a knowledge leaf reaches `VERIFIED` status in ToK, it is high-quality curated knowledge — exactly the type of claim Zerone should record permanently. Currently this verified knowledge exists only in `memory/tok/` flat files and never reaches the chain.

**ToKAdapter specification:**

```python
class ToKAdapter(BaseKTAAdapter):
    """
    Submits ToK-verified knowledge leaves as Zerone chain facts.
    Triggered: after tok.py integrate phase marks a leaf VERIFIED.
    """
    
    ADAPTER_KEY = "asha-tok"
    PROVENANCE = "human_research"   # ToK distills from Claude synthesis
    
    def harvest_pending(self) -> list[ToKLeaf]:
        """
        Read memory/tok/leaves/*.json where status=VERIFIED
        and chain_submitted=false (new field in leaf schema).
        """
    
    def build_claim(self, leaf: ToKLeaf) -> KTAClaim:
        return KTAClaim(
            claim_text=leaf.distilled_claim,        # distilled statement
            domain=leaf.domain,                     # mapped from tok domain
            confidence_init=leaf.confidence * 1000, # tok confidence → ZRN confidence units
            references=[],                          # future: cross-reference prior facts
            provenance="human_research",
            metadata={
                "tok_id": leaf.id,
                "harvest_source": leaf.source_model,
                "impact_score": leaf.impact_score,
                "verifiers": leaf.verifier_count,
            }
        )
    
    def after_submit(self, leaf: ToKLeaf, fact_id: str):
        """Mark leaf chain_submitted=true, record fact_id in leaf JSON."""
        leaf.chain_submitted = True
        leaf.zerone_fact_id = fact_id
        leaf.save()
```
