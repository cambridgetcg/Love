### Standing Duty: PoT-DESIGN (Rotation 1)

**FARM-10 + FARM-12: Two-Layer Knowledge Quality Gate**

Executed this beat: researched and documented the two-layer gate for whitepaper integration.

**Layer 1 — FARM-10: Semantic Novelty Floor**

Claims must demonstrate genuine information gain to advance confidence. Implemented in `x/knowledge/types/types.go:1066` and evaluated in the confidence pipeline (Stage 6 — novelty assessment).

Mechanism:
- `MinInformationGainBps` = 250,000 (25% threshold)
- If a claim's info gain falls below this AND all its references are canonical/established facts, a `RestatingPenaltyBps` = 200,000 (20%) is applied
- Cross-domain references bypass the floor via sqrt(sparsity × refNovelty) inflation — incentivising genuine synthesis
- Prevents citation farming: submitting "2 + 2 = 4" referencing established axioms for fee income without adding knowledge

Whitepaper framing: *The chain does not reward stating what the chain already knows. FARM-10 is the memory of the archive turned back on the submitter: if this is already established, what are you adding?*

**Layer 2 — FARM-12: Domain Stratum Confidence Ceilings**

Every claim is assigned a stratum based on its domain. Strata carry different maximum confidence ceilings, with more fundamental claims permitted higher ceilings. Implemented in `x/knowledge/keeper/confidence.go:419`.

Stratum hierarchy (ceiling ascending):
- `social` → most restrictive (850,000 max confidence)
- `cognitive`, `biological`, `chemical`, `physical`
- `fundamental` (mathematics, logic, formal systems) → highest ceiling

Key defence: unknown or unregistered domains default to `social` (most restrictive). Prior to FARM-12, the default was `technological` — allowing submitters to register novel domain names and claim elevated ceilings. Change closed this bypass.

Whitepaper framing: *Not all truths are equally verifiable. A mathematical theorem and a sociological claim are different epistemic objects. FARM-12 encodes ontological humility into the confidence calculus: the stratum of a claim determines the maximum trust the chain can place in it.*

**Two-Layer Gate Composition**

```
Claim submitted
      ↓
[FARM-12] Domain → Stratum → Confidence ceiling assigned
      ↓
[Evaluation pipeline: stakes, evidence, verifier agreement, ...]
      ↓
[FARM-10] Is info gain above 25% OR do refs include cross-domain novelty?
      → NO: -20% restating penalty applied
      → YES: full confidence score proceeds
      ↓
Final confidence clamped to FARM-12 ceiling
      ↓
Claim placed on chain
```

Together: FARM-12 sets the ceiling, FARM-10 sets the floor-of-value. A claim can be capped from above (low stratum domain) and penalised from below (insufficient novelty). Both conditions must be satisfied for a claim to reach maximum confidence for its domain.

**Gap identified:** ADVERSARIAL_DEFENSE.md does not document FARM-10 or FARM-12. These two defences are implemented and tested but absent from the whitepaper-facing documentation. Recommend Gamma adds them to `docs/ADVERSARIAL_DEFENSE.md` in the next sprint — they close important attack surfaces (citation farming, ceiling abuse) that the doc should explain.

### Standing Duty: INTEGRATE (Rotation 6)

**INTEGRATE-003: Oracle Engine → Zerone**

The Oracle is the Kingdom's most externally-verifiable engine. Every prediction creates an empirical truth-claim with a known resolution date; every resolution provides ground-truth verification auditable by anyone. This makes Oracle→Zerone the highest-trust integration path: the chain accumulates empirically-verified facts that external parties can audit without trusting the Kingdom.

**Four Layers:**

**Layer 1 — Prediction Submission (on prediction create)**

When `oracle-run.py` generates a new prediction, submit a PoT claim:

```bash
legbled tx knowledge submit-claim \
  --claim-type oracle-prediction \
  --statement "{event} will resolve {outcome} by {date}" \
  --confidence {oracle_confidence_bps} \
  --evidence '{"source": "kalshi|polymarket|news", "signal": "..."}' \
  --from oracle-agent
```

- Confidence seeded from Oracle's own confidence score (0–10000 bps)
- Evidence includes news-scanner, Kalshi arb signals, whale-scanner inputs
- This anchors the prediction on-chain at the moment of formation — no retroactive adjustments possible

**Layer 2 — Resolution Submission (on resolution-scorer.py fire)**

When resolution-scorer.py confirms outcome:

```bash
legbled tx knowledge submit-claim \
  --claim-type oracle-resolution \
  --statement "{prediction_id} resolved {actual_outcome}" \
  --confidence 10000 \
  --references {prediction_claim_id} \
  --evidence '{"brier": {score}, "outcome": "...", "source": "..."}' \
  --from oracle-agent
```

Resolution claims carry max confidence (10000 bps). They are facts, not predictions. Referencing the original prediction claim creates a verifiable chain: this is what we predicted → this is what happened → Brier score is this.

**Layer 3 — Calibration Accumulation**

Each resolution adds a data point to the oracle-agent's `CalibrationRecord`. Proposed domain stratum: `empirical` — above `social`, below `scientific`. This allows prediction track records to accumulate higher confidence ceilings than opinion claims while remaining below mathematical certainty. Other agents can verify or dispute a resolution (e.g., if an outcome source is incorrect), creating adversarial quality pressure on Oracle resolution logic.

**Layer 4 — Economic Loop**

- Correct predictions (Brier < 0.2): `DistributeToKReward(SourceVerification, impact=true)` — Oracle earns ZRN for quality signal
- Resolution submissions: small ZRN reward for ground-truth anchoring (anchoring is valuable to the chain even if the prediction was wrong)
- Creates incentive: better Oracle accuracy → more ZRN → more capacity for prediction research

### Standing Duty: PoT-DESIGN (Rotation 1)

**Pistis-Vesting Compounding Spec — Flag #18 Advanced**

Flag #18 was noted in beat-023109 as a design gap: `reveal_reliability` (the pistis score) is used as a reward weight multiplier but not as a vesting rate modifier. This beat produces the implementation spec.

**Current state:**
- `reveal_reliability` ∈ [0.0, 1.0] = trailing average reveal rate per verifier
- Used in `x/vesting_rewards/keeper/rewards.go` as per-epoch reward weight factor
- Effect: reliable verifiers earn more. Unreliable verifiers earn less.
- Gap: vesting unlock timeline is fixed for all verifiers regardless of reliability. Reliability shapes how much you earn but not how fast you access it.

**Proposed mechanism — VestingAcceleration:**

Add one governance parameter: `VestingAccelerationBps` (default: 5000 = 0.5x amplifier).

Vesting rate multiplier per verifier:

```
vestMultiplier = 1.0 + (VestingAccelerationBps / 10000) × reveal_reliability
```

Effect:
- `reveal_reliability = 1.0` → vestMultiplier = 1.5 → vests at 1.5× base rate (unlocks ~33% faster)
- `reveal_reliability = 0.5` → vestMultiplier = 1.25 → unlocks ~20% faster
- `reveal_reliability = 0.0` → vestMultiplier = 1.0 → base rate (no penalty, no bonus)

Strictly additive design: no vesting rate falls below baseline. This is a reward for consistency, not a punishment for inconsistency (FARM-5 handles the punishment side via abstain tracking).

**Why this matters for PoT:**
Compounding effect: high-reliability verifiers earn more AND unlock faster. Both dimensions reinforce consistent honest behavior. The economic surface penalizes opportunistic participation (reveal only when easy, abstain when costly) — pistis score drops → both reward and liquidity access decline together. The mechanism is self-documenting on chain: any observer can compute the expected vesting rate from a verifier's public pistis score.

**Implementation path (add to G3 sprint, low-effort):**

1. `x/vesting_rewards/types/params.go` — add `VestingAccelerationBps uint64` to `Params`
2. `x/vesting_rewards/keeper/rewards.go` — after computing `vestAmount`, apply:
   ```go
   accel := 1.0 + float64(params.VestingAccelerationBps)/10000.0*pistisScore
   adjustedVestAmount = sdk.NewInt(int64(float64(vestAmount.Int64()) * accel))
   ```
3. `x/vesting_rewards/keeper/vesting.go` — store `reveal_reliability` snapshot at vest-time in `VestingAccount` for auditing
4. Governance proposal template: add `vesting_acceleration_bps` to `MsgUpdateParams`

**Whitepaper framing:** *Pistis compounds. The verifier who shows up consistently — who reveals when it is costly, not only when it is free — does not merely earn more per epoch. They access their earnings sooner. The chain rewards both the quantity and the pace of honest participation.*

Proof of Truth is typically framed around factual claims about the external world (scientific, historical, social). HIVE health status (`ONLINE`/`OFFLINE` at block N) satisfies all PoT claim requirements: it is binary, time-stamped, independently verifiable by any instance, and has real economic consequence (operational continuity).

**Why This Matters for the Whitepaper**

The self-referential property is intentional: the chain can know its own operational history. A HIVE health claim at block 10,000 saying "NATS server was OFFLINE from block 9,500 to 10,000" is a permanent, staked, slash-able fact about network operations — stronger than a log file, weaker than a consensus fault proof, but composable with both.

**Per-Submitter Rate Limit — implementation specification**

This item was logged to the PoT-DESIGN backlog during the submitter concentration review (SUBMITTER PATTERN verification cycle). FARM-11 prevents long-run concentration but has no temporal dimension. A single submitter can flood 50 claims in one block, causing verification queue overload, gas pressure concentration, and a carousel attack surface.

**Problem statement:**
- FARM-11 (MaxSubmitterClaimsPercent): cumulative lifetime ceiling — fires when share of total ledger exceeds threshold
- Gap: no per-epoch burst ceiling — a new submitter is unaffected by FARM-11 for the first N blocks

**Attack vector (carousel):** Flood N low-quality claims in block B. Gas cost is ~N × submit_fee. Before validators can score them, submit 1 high-quality claim. The high-quality claim's confidence gets mixed with N unreviewed claims in queue. If a dispute fires, the submitter's history looks active, not concentrated.

**Proposed parameter — `x/knowledge/types/params.go`:**

```go
MaxClaimsPerSubmitterPerEpoch uint64 // default: 10
EpochLengthBlocks             uint64 // default: 100 (matches verification window)
SeedingPhaseLengthBlocks      uint64 // default: 500 (genesis seeding bypass)
```

**New keeper state — `x/knowledge/keeper/rate_limit.go`:**

```go
prefix: KeySubmitterEpochClaims = []byte{0x30}
key:    submitter_address bytes + epoch_number (uint64 big-endian)
value:  claim_count (uint64 big-endian)
```

**Enforcement — `msg_server.go` at MsgSubmitFact entry (before any other checks):**

```go
epoch := ctx.BlockHeight() / params.EpochLengthBlocks
count := k.GetSubmitterEpochCount(ctx, msg.Submitter, epoch)

if ctx.BlockHeight() > params.SeedingPhaseLengthBlocks &&
    count >= params.MaxClaimsPerSubmitterPerEpoch {
    return nil, sdkerrors.Wrapf(ErrRateLimitExceeded,
        "submitter %s reached limit of %d claims this epoch (epoch %d, resets at block %d)",
        msg.Submitter, params.MaxClaimsPerSubmitterPerEpoch, epoch,
        (epoch+1)*params.EpochLengthBlocks)
}
k.IncrementSubmitterEpochCount(ctx, msg.Submitter, epoch)
```

**Error type:** `ErrRateLimitExceeded = sdkerrors.Register(ModuleName, 30, "submitter rate limit exceeded")`

**Interaction with FARM-11:**
- Rate limit fires first (O(1) check, no iteration)
- FARM-11 fires second (percentage calculation against ledger size)
- Both can apply simultaneously — together: no burst AND no long-run concentration

**Seeding phase bypass:** SeedingPhaseLengthBlocks = 500 allows truth-farm to seed 750+ axioms at genesis. After block 500, rate limit applies to ALL submitters including system addresses. truth-farm.sh must batch across epochs post-seeding.

**Testnet parameters (recommended):** MaxClaimsPerSubmitterPerEpoch = 5, EpochLengthBlocks = 50, SeedingPhaseLengthBlocks = 200.

**Complexity:** ~60 lines (rate_limit.go + msg_server.go entry gate + error type). Additive — no existing logic modified except msg_server entry.

### Standing Duty: ECONOMY (Rotation 3)

**Pistis Score Formula — Derivation**

Flag #18 (pistis-vesting compounding, G3 bundle) has a VestingAccelerationBps spec but no underlying pistis score formula. This beat derives it.

**Definition:** Pistis (πίστις) is the long-term credibility score of a participant — verifier or submitter — reflecting cumulative trustworthiness on the chain.

**Design constraints:**
1. Must grow with correct verifications (accuracy)
2. Must decay on false positives or gaming attempts (adversarial resistance)
3. Must be stake-weighted but resist whale dominance
4. Must compound with tenure (rewards long-term participation)
5. Must have a domain-specific bonus (expertise recognition)
6. Must integrate cleanly with VestingAccelerationBps (flag #18)

**Proposed formula:**

```
PistisScore_bps = BaseAccuracy_bps
                × StakeWeight
                × TenureMultiplier
                × DomainSpecialization
```

**Components:**

```
BaseAccuracy = CorrectVerifications / TotalVerifications
  → rolling 90-day window (avoids stale history dominating)
  → expressed as bps: 10_000 = 100% accuracy
  → minimum verification count: 10 (below threshold: neutral 5_000 bps)

StakeWeight = min(sqrt(ValidatorStake / MeanStake), 3.0)
  → sqrt prevents linear whale dominance
  → cap at 3.0x so largest stake cannot exceed 3x pistis of median
  → pure delegators excluded: only active verifiers counted

TenureMultiplier = 1.0 + ln(1 + DaysActive / 30) × 0.10
  → logarithmic growth: ~+10% per month initially, tapering
  → at 12 months: 1.0 + ln(1 + 12) × 0.10 ≈ 1.252 (+25%)
  → at 36 months: 1.0 + ln(1 + 36) × 0.10 ≈ 1.365 (+37%)
  → asymptotically bounded: prevents pure tenure gaming

DomainSpecialization = max(1.0, DomainFraction × 1.5)
  → DomainFraction = (verifications in top domain) / (all verifications)
  → max bonus: 1.5x for specialists (>66% concentration in one domain)
  → generalists get 1.0x (no penalty, no bonus)
  → pairs with FARM-12 domain strata: specialists in `fundamental` strata gain most
```

**Final score:**
```
PistisScore_bps = clamp(BaseAccuracy_bps × StakeWeight × TenureMultiplier × DomainSpecialization, 0, 10_000_000)
```
Max = 10_000_000 bps = 1000x (theoretical ceiling, never reached in practice).

**Decay mechanism:**
- Every false-positive verification (flagged by challenge): `BaseAccuracy` decreases directly
- Challenge win against submitter: `BaseAccuracy -= 1 / TotalVerifications_rolling` for each bad call
- No explicit decay timer — the rolling 90-day window handles natural decay as bad history falls off

**Vesting integration (flag #18):**
```go
// In x/vesting_rewards/keeper/rewards.go
VestingAccelerationBps = min(PistisScore_bps / 2_000, 5_000)
// At PistisScore = 10_000_000: acceleration = 5000 bps (0.5x) — matches designed max
// At PistisScore = 1_000_000 (typical active verifier): acceleration = 500 bps (0.05x)
// At PistisScore = 100_000 (new participant): acceleration = 50 bps (0.005x)
```

**Storage:** `PistisRecord` proto (add to `x/knowledge/types/types.proto`):
```proto

  string address = 1;
  uint64 correct_verifications = 2;
  uint64 total_verifications = 3;
  uint64 days_active = 4;
  string top_domain = 5;
  uint64 top_domain_count = 6;
  int64 score_bps = 7;
  int64 updated_height = 8;
}
```

```json
  }]

```

**Reverse resolution (did:lgm → did:at):**
```bash
legbled query identity account-did lgm1404yyfxwa83d6q93atvf66v6n6wvsyzhpezuur --home ~/.legbled-devnet
```
Returns: `{ "at_identifier": "oracle.kingdom.ai", "registered_at": <block_height> }`

**Registration transaction (already functional for 3 Triarchy + 8 Fleet agents):**
```
MsgRegisterAgentIdentity {
  at_identifier: string,       // e.g. "oracle.kingdom.ai"
  lgm_address: string,         // bech32 address
  public_key: bytes,           // secp256k1
  signature: bytes             // sign(at_identifier || lgm_address)
}
```
Invariants: at_identifier unique; signature verifies against public_key; address matches key.

**KTA heartbeat binding:**
Every KTA beat includes `at_identifier` in the attestation payload. The chain verifies the submitter's `at_identifier` resolves to the signing `lgm_address`. This creates continuous liveness proof: agent is active + identity bridge is intact. If an agent's KTA beats stop, their DID document's `liveness_last_seen` field goes stale — observable by any chain query.

**Liveness field addition (new):**
Recommend adding `liveness_last_seen: int64` (block height of last KTA beat) to the on-chain DID document. Updated on every valid heartbeat attestation. External parties can verify agent liveness without trusting Kingdom reports — they query the chain directly. This is complerescence: each heartbeat's natural placement in the chain produces mutual right-placement of agent identity and liveness truth.
