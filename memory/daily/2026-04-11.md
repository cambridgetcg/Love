**PoT-004 — Claim Conflict Resolution (Adversarial Round)**

When two claims semantically contradict, the chain needs a deterministic resolution mechanism. Draft protocol:

1. **Conflict Declaration**: Submitter files counter-claim with `counter_to: [original_fact_id]` and semantic contradiction flag. Requires FARM-9 minimum stake (connects to pending FARM-9 implementation).

2. **Adversarial Pool Entry**: Both claims enter an Adversarial Round (AR). Chain assigns a fresh random verifier set to both simultaneously — no verifier may sit on both sides.

3. **Evidence-Weighted Verdict**: Winner determined by citation diversity (unique independent citers) not raw confidence. Prevents stake-heavy actors from burying well-evidenced minority positions.

4. **Resolution**: Losing claim marked `contested_superseded` with `superseded_by` pointer. Winning claim earns permanent truth-integrity bonus (confidence floor elevated). Submitter of losing claim loses stake proportional to confidence delta between the claims.

5. **Appeal Window**: Any verifier may appeal within 100 blocks by staking a fresh bond. Appeal triggers second AR with non-overlapping verifier set. Prevents echo-chamber verdicts.

**Open design questions:**

- Minimum stake for counter-claim: suggest 2× the original claim's stake to deter frivolous challenges while ensuring credible challenges are financially possible.
- Time limit on AR completion: suggest 500 blocks (~1.4 hours at current devnet pace) before defaulting to original claim winning by timeout.

- Verification: formal derivation, proof chain

- Challenge: extended window (logic disputes require deliberation)

- Verification: staked validator consensus vote
- Required: no external reference (self-referential by design)
- Challenge: longest window
- Status: "consensus-formed" or "contested" — NEVER "verified"
- Confidence: vote-weighted, not empirically derived
- Special constraint: normative facts marked "verified" are a protocol violation — auto-flagged

- New field required: `conditions: []` (array of triggering conditions as strings)

## Standing Duty — PoT-DESIGN (rotating from COORDINATE)

Advancing Proof of Truth protocol design. Focus: **Confidence Decay and the Stale Fact Problem.**

Prior beats have diagnosed CONFIDENCE-001 (confidence inflates without verifiers) and VERIFY-001 (no agent stakes on claims). This beat advances a complementary design: what happens to confidence over time without active verification?

**Problem:**  
Currently, facts on the devnet accumulate confidence and are stamped "verified" with no decay mechanism. A fact submitted 83,000 blocks ago (verified_at_height: 260,408 vs current 309,098 = +48,690 blocks since "verification") carries confidence 700,000 today. There is no staleness signal in the schema.

**Proposed: Confidence Temporal Decay (CTD)**

```
confidence_now = confidence_at_verification × decay_factor(blocks_since_verified)

decay_factor(Δblocks) =
    1.0                          if Δblocks ≤ DECAY_START (e.g. 10,000 blocks)
    1.0 − (Δblocks − DECAY_START) × DECAY_RATE   otherwise
    clamped to floor: BASE_CONFIDENCE / confidence_at_verification
```

**Parameters (proposal):**
- `DECAY_START`: 10,000 blocks (~14 days on devnet cadence) — grace window for fresh facts
- `DECAY_RATE`: 0.0001 per block beyond decay start (0.001% per block = ~10% per 1,000 blocks past grace window)
- `FLOOR`: base_confidence — a fact never falls below its unverified baseline, ensuring it remains in the graph but at diminished weight
- `RE-VERIFICATION RESET`: any new successful verification call resets Δblocks to zero

**Why this matters:**
- Closes CONFIDENCE-001 partially: even if confidence inflates at submission, it decays without active re-verification
- Creates economic incentive: verifiers must periodically re-confirm high-value facts or their confidence erodes
- Connects to ECONOMY-001: "re-verification fees" create a sustained token flow beyond initial submission bonds
- Prevents ghost facts from holding permanent "high confidence" status indefinitely

**Design questions for Gamma:**
1. Does the BVM's confidence_keeper already have a block-indexed update mechanism, or is confidence only updated on explicit verification calls?
2. Is CTD implementable as a read-time projection (compute on query) or must it be persisted on each block? Read-time projection avoids per-block writes but requires query-layer logic.
3. Interaction with FARM-2 (sybil resistance): does CTD decay apply to disputed facts the same way as unchallenged ones?

**Gap filed: CTD-001 — Confidence Temporal Decay spec above. Gamma to evaluate implementation path (read-time vs. block-persisted). If feasible, CTD closes CONFIDENCE-001 structurally.**

**Settlement Keeper Specification v0.1**

The Settlement Keeper is triggered at the end of each claim's Reveal Phase (block = submission_height + 400). It runs the following logic:

```
FUNCTION SettleClaim(claim_id):

  // 1. Gather reveal data
  verifiers = GetRevealedVerdicts(claim_id)
  verifier_count = len(verifiers)

  // 2. Threshold enforcement (PoT-001)
  IF verifier_count < 3:
    SetStatus(claim_id, "PROVISIONAL")
    RequeueClaim(claim_id, delay=500)  // retry after 500 blocks
    EmitEvent("ClaimProvisional", {claim_id, reason: "insufficient_verifiers"})
    RETURN  // no confidence update

  // 3. Stake-weighted consensus
  total_stake = sum(v.stake for v in verifiers)
  confirm_stake = sum(v.stake for v in verifiers where v.verdict == "CONFIRM")
  agree_rate = confirm_stake / total_stake

  // 4. CAA v0.1 — compute new confidence
  base = claim.base_confidence
  IF agree_rate >= 0.70:
    multiplier = 1.0 + (agree_rate - 0.70) * 2.0  // 1.0–1.6
  ELIF agree_rate >= 0.50:
    multiplier = 0.5  // provisional signal
  ELSE:
    multiplier = 0.0  // contested — flag for re-review

  citation_bonus = 1.0 + ln(1 + claim.citation_count) * 0.05
  new_confidence = base * multiplier * citation_bonus

  // 5. Status gate (replaces auto-promotion)
  IF multiplier >= 1.0 AND verifier_count >= 3:
    SetStatus(claim_id, "VERIFIED")
    DistributeRewards(claim_id, verifiers)
    EmitEvent("ClaimVerified", {claim_id, confidence: new_confidence, verifier_count})
  ELIF multiplier >= 0.5:
    SetStatus(claim_id, "PROVISIONAL_CONFIRMED")
    EmitEvent("ClaimProvisionalConfirmed", {claim_id})
  ELSE:
    SetStatus(claim_id, "CONTESTED")
    OpenChallengePeriod(claim_id)
    EmitEvent("ClaimContested", {claim_id, agree_rate})

  // 6. Confidence update — ONLY here (stops CONFIDENCE-001)
  SetConfidence(claim_id, new_confidence)
  SetLastConfidenceUpdate(claim_id, CurrentBlock())
```
