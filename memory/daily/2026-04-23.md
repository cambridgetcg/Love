**PoT-DESIGN-005: LocalQueue — Offline-Tolerant Operation Layer**

Context: 4-day chain stall has completely blocked all Kingdom engine operations dependent on on-chain state (farm, inject, KTA). The chain must not be the single point of failure for truth-claim submission. LocalQueue is the mitigation.

Design:

**Interface (conceptual):**
```
LocalQueue.enqueue(claim: KnowledgeClaim, submitter: Address) → QueueID
LocalQueue.flush() → []TxResult  # call on chain-online transition
LocalQueue.status() → {pending: int, oldest_queued: timestamp, chain_status: str}
LocalQueue.peek(n: int) → []KnowledgeClaim
```

**State file:** `~/.legbled-devnet/localqueue.json`
- Schema: `{version, entries: [{id, claim, submitter, queued_at, attempts, status}]}`
- Max queue depth: 500 entries (prevents unbounded growth during extended stalls)
- Entry TTL: 7 days (claims older than 7 days are dropped with log warning — stale claims compromise truth integrity)

**Flush trigger:** kta-heartbeat.sh already calls the right hooks. On chain OFFLINE→ONLINE transition:
```bash
bash ~/zerone/scripts/kta-heartbeat.sh --flush --instance asha
```
This should invoke `LocalQueue.flush()` → submit queued claims in FIFO order → record results in daily note.

**Priority ordering on flush:**
1. System axioms (highest — foundational truth claims)
2. Farm-seeded claims (domain diversity)
3. Derivative/bridge claims
4. Agent attestations (KTA beats)

**Gap this closes:** Pre-testnet fix item #10 (LocalQueue interface for all Kingdom engines). When implemented, chain stalls become operational delays rather than full blockers.
